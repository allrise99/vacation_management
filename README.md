# 연차 관리 (vacation_management)

PC와 스마트폰에서 **남은 연차와 사용 기록**을 쉽게 확인하는 개인용 웹 대시보드입니다.
모바일 우선 반응형으로 만들었고, React + Vite + TypeScript로 구현했습니다. 런타임 의존성은 `react`, `react-dom`뿐입니다.

> 🔄 **기기 간 동기화는 선택 기능입니다.**
> 기본적으로 데이터는 지금 사용하는 기기의 브라우저(localStorage)에만 저장되며, **자동으로 동기화되지 않습니다.**
> [Supabase 동기화](#기기-간-동기화-supabase)를 설정하고 이메일로 로그인한 기기끼리만 기록이 자동으로 합쳐집니다.
> 동기화를 쓰지 않을 때는 **설정(⚙) → 백업 파일 내려받기**로 만든 파일을 다른 기기에서 **백업 복원**해서 옮기세요.

## 주요 기능

| 기능 | 설명 |
| --- | --- |
| 연도별 연차 부여일수 | 연도마다 총 연차 부여일수를 직접 설정합니다 (0.5일 단위). |
| 휴가 등록·수정·삭제 | 연차는 종일·오전반차·오후반차 중에서 고릅니다. 반차는 0.5일 차감됩니다. |
| 사용 완료 / 사용 예정 | 날짜로 자동 구분합니다. 오늘까지는 사용 완료, 내일부터는 사용 예정입니다. 오늘에 걸친 기간은 나눠서 계산합니다. |
| 현황 | 총 부여, 사용 완료, 사용 예정, 현재 잔여, 예정 반영 후 잔여를 보여 줍니다. |
| 달력·목록·연도 조회 | 월별 달력, 상태·종류 필터가 있는 사용 내역 목록, 상단 연도 선택을 제공합니다. |
| 모바일 UI | 잔여일수를 큰 카드로 보여 주고, 화면 하단에 고정된 `+ 연차 추가` 버튼을 둡니다. |
| 기기 간 동기화 (선택) | Supabase를 설정하면 이메일 로그인으로 PC·휴대폰 기록을 자동으로 합칩니다. 오프라인에서도 먼저 기기에 저장됩니다. |
| 백업·복원 | JSON 파일로 내보내고 가져옵니다. 복원할 때 형식을 검증합니다. |
| 예시 데이터 | 가상 기록으로 화면을 체험합니다. 예시 기록은 저장되지 않으며 실제 기록과 섞이지 않습니다. |

### 휴가 규칙

- **연차**
  - 부여일수는 연도별로 직접 설정합니다.
  - 종일 연차는 기간 안의 평일 수만큼 자동으로 차감합니다. 공휴일이 끼면 차감일수를 직접 고칠 수 있습니다.
  - 남은 연차(예정 반영 후) 중 **최대 5일까지만 보상**됩니다. 나머지는 소멸되는 것으로 표시합니다.
- **특별휴가**
  - 연 5일이며 종일 단위로만 씁니다(반차 불가).
  - **한 번 나눠 쓸 수 있습니다.** 즉, 연간 최대 2회입니다(예: 3일 + 2일).
  - 남은 일수가 있어도 **보상되지 않습니다.**
- 연도가 바뀌는 기간은 연도별로 나눠서 등록합니다. 날짜가 겹치는 기록은 막습니다. 같은 날 오전반차와 오후반차를 함께 쓰는 것은 허용합니다.

## 로컬 실행

Node.js 20 이상이 필요합니다.

```bash
npm install
```

```bash
npm run dev
```

브라우저에서 <http://localhost:5173/vacation_management/>를 엽니다.
같은 와이파이의 스마트폰에서 확인하려면 `npm run dev -- --host`로 실행하고, 화면에 표시된 Network 주소로 접속하세요.

그 밖의 명령:

```bash
npm test          # 연차 계산·저장·동기화 로직 단위 테스트 (Vitest)
npm run build     # 타입 검사 + 프로덕션 빌드 (dist/)
npm run preview   # 빌드 결과 미리보기
```

## GitHub Pages 배포

`vite.config.ts`의 `base`가 `/vacation_management/`로 설정되어 있습니다. 배포 주소는 `https://<GitHub 사용자명>.github.io/vacation_management/`입니다.

1. GitHub 저장소에서 **Settings → Pages → Build and deployment → Source**를 **GitHub Actions**로 바꿉니다.
2. `main` 브랜치에 push하면 `.github/workflows/deploy.yml`이 실행됩니다. 순서는 테스트 → 빌드 → Pages 배포입니다.
3. **Actions** 탭에서 진행 상황을 확인합니다. 수동으로 실행하려면 `Deploy to GitHub Pages` 워크플로에서 **Run workflow**를 누릅니다.

저장소 이름을 바꾸면 `vite.config.ts`의 `base`도 같은 이름으로 바꿔야 합니다.

## 기기 간 동기화 (Supabase)

[Supabase](https://supabase.com)(무료 요금제로 충분)를 동기화 저장소로 씁니다. 설정하지 않으면 앱은 지금처럼 기기 저장만 합니다.

### 동작 방식

- **로컬 우선**: 입력은 항상 이 기기에 먼저 저장되고, 로그인되어 있으면 서버와 맞춥니다. 인터넷이 끊겨도 쓸 수 있고, 연결되면 올라갑니다.
- **동기화 시점**: 로그인 직후, 수정하고 약 1초 뒤, 앱을 다시 열거나 돌아왔을 때, 인터넷 재연결 시, 열려 있는 동안 1분마다.
- **합치는 규칙**: 휴가 기록 하나, 연도 설정 하나 단위로 합칩니다. 두 기기에서 **같은 기록**을 따로 고치면 **나중에 고친 쪽**이 남습니다. 서로 다른 기록은 모두 남습니다.
- **삭제**: 지운 기록은 "삭제됨" 표시를 남겨서 다른 기기에서도 지워지고, 다시 살아나지 않습니다.
- **처음 로그인할 때**: 그 기기에 이미 있던 기록도 계정에 함께 올라가 합쳐집니다.
- **로그아웃**: 그 기기에서만 로그아웃되고, 그 기기의 기록은 남습니다.
- **로그인 중 백업 복원·전체 삭제**: 다른 기기와 서버에도 똑같이 반영됩니다(복원한 내용으로 바뀌거나 모두 삭제됨).
- **보안**: 데이터베이스 행 수준 보안(RLS)으로 로그인한 본인 기록만 읽고 쓸 수 있습니다.

### 1. Supabase 프로젝트 만들기

1. <https://supabase.com>에 가입하고 **New project**를 만듭니다. 지역은 Seoul(Northeast Asia)을 권장합니다.
2. 왼쪽 메뉴 **SQL Editor**를 열고, 이 저장소의 [`supabase/schema.sql`](supabase/schema.sql) 내용을 전부 붙여 넣은 뒤 **Run**을 누릅니다.
   - `leave_records` 테이블, 본인 기록만 접근하는 RLS 정책, 오래된 수정이 최신 기록을 덮어쓰지 못하게 막는 트리거가 만들어집니다.

### 2. 로그인(Auth) 설정

1. **Authentication → Sign In / Providers**에서 **Email**이 켜져 있는지 확인합니다.
2. **Authentication → URL Configuration**
   - **Site URL**: `https://<GitHub 사용자명>.github.io/vacation_management/`
   - **Redirect URLs**에 위 주소를 추가합니다. 로컬에서도 쓰려면 `http://localhost:5173/vacation_management/`도 추가합니다.
3. (권장) **Authentication → Emails → Magic Link** 템플릿에 숫자 코드 `{{ .Token }}`를 넣습니다. 예: `<p>로그인 코드: {{ .Token }}</p>`.
   메일을 다른 기기나 메일 앱 안 브라우저에서 열어도, 앱에 코드를 입력해서 로그인할 수 있습니다.
4. (권장) 사용할 기기에서 **처음 로그인을 마친 뒤** **Authentication → Sign In / Providers**에서 **Allow new users to sign up**을 끕니다. 그러면 다른 사람이 이 앱 주소로 계정을 만들 수 없습니다. RLS 덕분에 다른 사람은 원래도 내 기록을 볼 수 없지만, 내 프로젝트에 남의 데이터가 쌓이는 것까지 막아 줍니다.

> Supabase 기본 메일 발송은 시간당 보낼 수 있는 수가 적습니다. "메일을 너무 자주 요청했습니다"가 나오면 잠시 후 다시 시도하세요. 한 번 로그인하면 기기마다 로그인이 유지되므로 자주 받을 일은 없습니다.

### 3. 연결 정보 넣기 (소스코드에 넣지 않음)

**Project Settings → API**(또는 상단 **Connect**)에서 두 값을 확인합니다.

- **Project URL**: 예) `https://abcd1234.supabase.co`
- **anon public key** 또는 **publishable key** (`sb_publishable_...`)

> 이 두 값은 브라우저에 공개되도록 만들어진 값이라 배포 파일에 들어가도 괜찮습니다. 데이터 보호는 RLS가 맡습니다.
> 단, **`service_role` 키나 `sb_secret_...` 키는 절대 넣지 마세요.** 앱은 이런 키를 넣으면 무시하도록 되어 있습니다.

**GitHub Pages 배포용**: 저장소 **Settings → Secrets and variables → Actions → Variables** 탭에서 **New repository variable**로 다음 두 개를 추가합니다.

| 이름 | 값 |
| --- | --- |
| `SUPABASE_URL` | Project URL |
| `SUPABASE_ANON_KEY` | anon 또는 publishable key |

그다음 **Actions → Deploy to GitHub Pages → Run workflow**로 다시 배포합니다. 변수가 없으면 동기화 없이 빌드됩니다.

**로컬 개발용**: `.env.example`을 `.env.local`로 복사해서 값을 채웁니다. `.env.local`은 `.gitignore`에 들어 있어 커밋되지 않습니다.

### 4. 기기마다 로그인

앱에서 **설정(⚙) → 기기 간 동기화**에 이메일을 입력하고 **로그인 메일 받기**를 누릅니다. **로그인할 기기에서** 메일의 링크를 누르거나, 메일에 적힌 숫자 코드를 앱에 입력합니다. 화면 위쪽에 `● 동기화됨 · 시각`이 보이면 완료입니다.

## 데이터 저장 방식과 한계

- **저장 위치**: 브라우저 `localStorage`의 `vacation-management:data:v1` 키입니다. 동기화에 로그인한 경우에만 본인 Supabase 프로젝트의 `leave_records` 테이블에도 저장됩니다. 그 밖의 곳으로는 전송되지 않습니다.
- **기기·브라우저마다 따로 저장**: PC Chrome, PC Edge, 스마트폰 Safari는 서로 다른 저장소를 씁니다. 동기화에 로그인하지 않은 브라우저끼리는 **자동 동기화가 되지 않습니다.**
- **사라질 수 있는 경우**: 브라우저 데이터(사이트 데이터)를 지우거나 시크릿·사생활 보호 모드를 쓰면 기록이 사라질 수 있습니다. iOS Safari는 오랫동안 방문하지 않은 사이트의 저장 데이터를 지울 수 있습니다.
- **백업 권장(동기화하지 않을 때 특히)**: 설정(⚙) → **백업 파일 내려받기**로 `vacation-backup-YYYYMMDD.json`을 주기적으로 저장하세요. 복원하면 현재 기기의 데이터가 백업 내용으로 **바뀝니다**(병합하지 않음).
- **동기화하지 않을 때**: 두 기기에서 따로 수정한 내용을 합치는 기능은 없습니다. 한 기기를 기준 기기로 정해 쓰세요.
- **동기화할 때의 한계**: 같은 기록을 두 기기에서 동시에 고치면 한쪽 수정만 남습니다(나중에 고친 쪽). 기기 시계가 크게 틀리면 순서 판단이 틀릴 수 있습니다. 두 기기에서 날짜가 겹치는 기록을 따로 넣으면 둘 다 남으니, 목록에서 확인해 지우세요. 다른 기기의 변경은 앱을 열거나 다시 볼 때(또는 1분마다) 받아옵니다.
- **동기화 중에도 백업 권장**: 실수로 지우면 모든 기기에서 지워지므로, 가끔 JSON 백업을 받아 두세요.

## 개인정보 보호

- 소스코드와 저장소에는 **실제 연차 기록이나 개인정보를 넣지 않습니다.** 공개 배포 파일(`dist/`)에도 개인 데이터가 들어가지 않습니다. 기록은 사용자의 브라우저와, 동기화에 로그인한 경우 본인 Supabase 프로젝트에만 저장됩니다.
- Supabase 연결 정보는 소스코드가 아니라 GitHub 저장소 변수(Variables)나 `.env.local`로 넣습니다. 배포 파일에는 공개용 키만 들어가며, 비밀 키(`service_role`, `sb_secret_`)는 앱이 쓰지 않습니다.
- 동기화 테이블은 RLS로 보호되어 로그인한 본인 기록만 읽고 쓸 수 있습니다. 로그인 메일 주소는 Supabase 인증에만 쓰입니다.
- 백업 파일(`vacation-backup*.json`)은 `.gitignore`에 등록되어 있습니다. 실수로 커밋하지 않도록 저장소 폴더 밖에 보관하세요.
- 예시 데이터는 코드가 만든 가상 기록입니다. 메모에 `[예시]`가 붙고, id가 `demo-`로 시작하며, 화면 상단에 "예시 데이터 보기 중" 배너가 표시됩니다. localStorage에는 저장되지 않습니다.
- 배포 페이지에는 `noindex`가 설정되어 검색 엔진 색인을 요청하지 않습니다. 다만 GitHub Pages 주소 자체는 공개입니다(저장된 기록은 각자의 브라우저에만 있습니다).

## 프로젝트 구조

```
src/
  lib/
    date.ts          날짜 유틸 (로컬 YYYY-MM-DD 문자열 기반)
    leave.ts         연차 계산·검증 로직 (잔여일수, 보상, 특별휴가 규칙)
    storage.ts       localStorage 저장, JSON 백업·복원 검증
    sync.ts          동기화 병합 로직 (기록 단위 최신 우선, 삭제 전파)
    supabase.ts      Supabase 연결 (설정이 있을 때만 불러옴)
    useSync.ts       로그인 상태·동기화 시점 관리 (React 훅)
    demo.ts          가상 예시 데이터
    *.test.ts        단위 테스트
  components/        요약 카드, 달력, 목록, 입력 폼, 설정 시트, 동기화 상태·로그인
  App.tsx            화면 조립·상태 관리
.github/workflows/deploy.yml   GitHub Pages 자동 배포
supabase/schema.sql            동기화 테이블·보안 정책 (Supabase SQL Editor에서 실행)
.env.example                   로컬 개발용 Supabase 설정 예시
```
